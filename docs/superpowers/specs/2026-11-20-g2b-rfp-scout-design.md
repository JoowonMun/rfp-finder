# 나라장터 공고 추천 스킬 (g2b-rfp-scout) 설계

작성일: 2026-11-20

## 1. 왜 만드나

AX컨설팅 팀의 올해 사업이 끝나서 내년 사업을 찾아야 한다. 나라장터에는 매일 공고가 쏟아지지만 사람이 일일이 제안요청서를 열어 "우리가 제안 쓸 만한가"를 판단하기엔 양이 많다. 이 스킬은 공고와 제안요청서(RFP)를 수집·분석해서 **제안을 써볼 만한 공고를 골라** 팀 노션 표에 쌓아준다.

Claude Code 스킬로 만드는 이유: 팀원 각자가 자기 Claude 계정으로 돌릴 수 있고, 다른 팀에도 배포할 수 있다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
- 나라장터 용역 입찰공고와 사전규격을 주기적으로 수집한다.
- 제안요청서 첨부파일(HWP, HWPX, PDF)을 내려받아 **본문까지** 읽고 판단한다.
- 팀 프로필(관심 분야, 역량, 제외 조건)에 비춰 적합도를 매기고, 요약·상세 분석을 노션 DB에 올린다.
- 판단 기준은 설정 파일로 분리해 어느 팀이든 자기 기준으로 쓸 수 있다.
- 한 사람이 정기 실행하는 것을 기본으로 하되, 누가 언제 돌려도 같은 공고가 중복으로 쌓이지 않는다.

**비목표 (v1에서 안 함)**
- 입찰 참여 자체(투찰, 서류 제출) 자동화
- 제안서 초안 작성
- 사전규격 ↔ 이후 본공고 자동 연결 (나중에 고려)
- 경쟁사·과거 낙찰 분석

**실패 조건 (돌아가도 실패인 경우)**
- "AI"라는 단어만 들어간 단순 유지보수·물품 구매가 상위에 올라와 표가 쓰레기로 찬다.
- 같은 공고가 여러 줄로 쌓인다.
- 변환이 실패한 RFP를 읽은 척 그럴듯한 분석을 쓴다. (못 읽었으면 못 읽었다고 표시해야 한다.)
- 설치가 너무 번거로워 팀원이 안 쓴다.

## 3. 제약

- 데이터 출처는 **공공데이터포털 조달청 OpenAPI** (입찰공고정보서비스, 사전규격정보서비스). 나라장터 화면 스크래핑은 하지 않는다. 사용자마다 서비스키 발급 필요.
  - 2025년 나라장터 차세대 전환 이후 엔드포인트·필드명이 바뀌었을 수 있다. 구현 첫 단계에서 실제 호출로 명세를 확인한다.
- 노션은 **Notion API(내부 통합 토큰)** 로 연동한다. 파일 첨부는 File Upload API(생성 → 전송 → 1시간 안에 페이지 files 속성에 연결) 사용.
- 실행 환경: Windows 11 PC, Python 3.10+. 배포 대상도 대부분 Windows 가정.
- RFP는 수십~백 페이지라 그대로 넣으면 길다. 분석에 필요한 부분 위주로 넘겨야 한다.

## 4. 검토한 방식

| 안 | 내용 | 장점 | 단점 | 결론 |
|---|---|---|---|---|
| **A. 스킬 + 보조 스크립트** | 반복 작업(API 조회, 다운로드, 변환, 노션 업로드·중복 체크)은 Python 스크립트, 판단(적합도, 요약, 분석)은 Claude | 결과가 일정, HWP 처리 가능, 파일 첨부·중복 체크 확실 | 처음 1회 Python·서비스키·노션 토큰 설정 필요 | **채택** |
| B. 스킬만 (스크립트 없음) | Claude가 매번 API 호출, 노션 커넥터로 업로드 | 설치 거의 없음 | HWP 변환 불가 → 본문 분석이라는 핵심 요구 실패, 파일 첨부 어려움, 실행마다 결과 들쭉날쭉 | 탈락 |
| C. 독립 프로그램 + Claude API | 파이썬 앱이 Claude API 직접 호출 | 가장 안정적 | 스킬이 아님, 각자 계정으로 돌린다는 취지와 어긋남, API 비용 별도 | 탈락 |

사용자 선택: **A**.

## 5. 전체 흐름

```
[스킬 실행: /g2b-rfp-scout]
  │
  1. 설정 로드 (없으면 첫 실행 인터뷰로 생성)
  2. collect.py   ── 공공데이터 API: 최근 N일 용역 입찰공고 + 사전규격 조회
  3. dedupe       ── 노션 DB의 공고번호 목록과 대조, 이미 있는 건 제외
  4. prefilter    ── 포함/제외 키워드, 예산 범위, 마감 임박 제외 → 후보 목록 (순수 스크립트, 6.8)
                     → 우선순위 정렬 후 상한(max_per_run)까지만 이번 실행에서 처리
  5. fetch_docs.py ── 후보의 첨부파일 다운로드 → 텍스트 변환 (HWPX/HWP/PDF)
  6. [Claude]     ── 후보별 RFP 텍스트 + 팀 프로필 → 적합도·요약·상세 분석 (JSON)
                     공고 1건 분석이 끝날 때마다 바로 7로 넘겨 업로드 (중간에 끊겨도 완료분은 남음)
  7. publish.py   ── 노션 DB에 행 생성 + 첨부파일 업로드 + 페이지 본문 작성
  8. 실행 결과 요약 출력 (신규 n건, ★★★ m건, 변환 실패 k건)
```

2~5, 7은 스크립트(결정적), 6만 Claude. 같은 입력이면 매번 같은 후보가 나오게 하려고 prefilter에는 Claude를 넣지 않는다.

### 6.2 설정 (사용자/팀별)

위치: `%USERPROFILE%\.g2b-rfp-scout\` (스킬 폴더 밖 → 스킬 업데이트해도 유지)

- `config.yaml` — 판단 기준 (팀 내 공유 가능, 비밀 없음)
- `.env` — `DATA_GO_KR_SERVICE_KEY`, `NOTION_TOKEN` (개인, 절대 공유·커밋 금지)

```yaml
team:
  name: AX컨설팅팀
  capabilities: |          # Claude가 적합도 판단에 쓰는 핵심 자료
    AI 전환(AX) 전략 컨설팅, 생성형 AI 도입 ISP/ISMP, AI 거버넌스,
    업무 프로세스 AI 적용 진단, PoC 기획 ... (팀이 자유롭게 서술)
  past_projects: |         # 선택, 실적 요건 판단에 도움
    ...
filters:
  include_keywords: [AI, 인공지능, 생성형, AX, 디지털전환, ISP, ISMP, 데이터, LLM]
  exclude_keywords: [유지보수, 유지관리, 구매, 임차, 물품, 공사]
  budget_min_krw: 50000000
  budget_max_krw: 3000000000
  min_days_to_deadline: 5   # 본공고에만 적용. 사전규격은 의견 마감이 지난 것만 제외
  include_pre_spec: true    # 사전규격 포함 여부
collect:
  lookback_days: 3          # 정기 실행 주기보다 약간 길게
  max_per_run: 15           # 한 번에 Claude가 분석할 공고 수 상한
notion:
  database_id: "..."
  max_upload_mb: 5          # 무료 요금제 파일당 한도. 유료면 늘림 (v1은 단일 업로드만, 분할 업로드 없음)
```

첫 실행 시 `config.yaml`이 없으면 스킬이 대화로 팀 소개·관심 분야·제외 조건을 물어 생성하고, 토큰 발급은 setup-guide로 안내한다.

### 6.3 첨부파일 확보와 HWP/문서 변환

**확보:** 입찰공고 API 응답의 규격서/첨부 URL 필드(차세대 전 기준 `ntceSpecDocUrl1~10`, `ntceSpecFileNm1~10`; 사전규격은 규격서 파일 필드)를 사용한다. 구현 첫 단계(스파이크)에서 실제 응답으로 확인한다.
- URL이 응답에 없거나 로그인이 필요한 링크뿐이면: 나라장터 화면 스크래핑으로 우회하지 않는다(제약 위반·유지보수 부담). 해당 공고는 변환 실패와 같은 경로(메타데이터만으로 판단 + 경고 표시)로 처리하고, **스파이크 결과를 사용자에게 보고한 뒤 다음 단계를 정한다.** 본문 분석이 핵심 요구이므로 이 경우는 조용히 넘어가지 않는다. *(설계자 판단)*

| 형식 | 방법 | 비고 |
|---|---|---|
| HWPX | zip 해제 → `Contents/section*.xml` 텍스트 추출 (표 포함) | 표준 라이브러리만으로 가능 |
| HWP (v5) | `pyhwp` (hwp5txt / hwp5html) | 표 구조 보존이 필요하면 html 경유 |
| PDF | `pdfplumber` 또는 `pypdf` | 스캔본(이미지 PDF)은 텍스트 없음 → 실패 처리 |
| ZIP | 해제 후 내부 파일에 위 규칙 적용 | 첨부가 묶음으로 오는 경우 |

- 공고당 첨부가 여러 개면 파일명으로 RFP(제안요청서·과업지시서)를 우선 선택하고, 나머지는 보조.
- 변환 실패 시: 해당 공고는 **공고 메타데이터만으로 1차 판단**하고 페이지에 "⚠ 제안요청서 변환 실패 — 원문 직접 확인 필요"를 표시, `RFP 분석` 속성을 `실패`로.
- LibreOffice 변환은 설치가 무거워 v1에서 제외.

### 6.4 Claude 분석

입력: 공고 메타데이터 + RFP 텍스트(길면 과업 내용·요구사항·평가 기준·참가 자격 섹션 우선 발췌) + `team.capabilities`.

출력 (공고당 JSON, 스크립트가 노션으로 변환):
```json
{
  "bid_no": "...",
  "fit": 3,                         // 1~3 (★)
  "fit_reason": "한두 문장",
  "summary": "한 줄 요약",
  "detail": {
    "overview": "사업 개요/기간/예산",
    "requirements": ["주요 요구사항", "..."],
    "why_fit": ["..."],
    "gaps": ["안 맞는 부분"],
    "eligibility_risks": ["실적 요건, 공동수급, 지역 제한 등"],
    "evaluation": "기술:가격 비율, 평가 방식",
    "rfp_read": true
  }
}
```

적합도 기준 (analysis-guide.md에 상세화):
- ★★★ 핵심 과업이 팀 역량과 직접 일치, 참가 자격 문제 없음
- ★★ 일부 일치(예: 구축 비중이 크지만 컨설팅 파트 존재), 또는 자격 리스크 있음
- ★ 키워드만 겹치고 실질적으로 안 맞음

### 6.5 노션 DB

팀 페이지 안에 표 DB 하나. `setup_notion_db.py`가 속성을 만들어준다.

| 속성 | 타입 | 설명 |
|---|---|---|
| 공고명 | title | |
| 구분 | select | 본공고 / 사전규격 |
| 발주기관 | text | |
| 예산 | number (원) | |
| 마감일 | date | 사전규격은 의견 마감일 |
| 적합도 | select | ★★★ / ★★ / ★ |
| 한줄 요약 | text | |
| 제안요청서 | files | 원본 첨부 업로드. 파일이 `notion.max_upload_mb`(기본 5, 무료 요금제 한도)를 넘거나 업로드 실패 시 나라장터 다운로드 링크(외부 파일)로 대체 |
| 원문 링크 | url | 나라장터 공고 상세 |
| 상태 | select | 검토전 / 검토중 / 참여 / 보류 / 자동제외 |
| RFP 분석 | select | 완료 / 실패 |
| 공고번호 | text | 중복 체크 키 (공고번호+차수) |
| 수집일 | date | |
| 수집자 | text | 누가 돌렸는지 |

페이지 본문: 6.4의 `detail`을 제목+목록 블록으로 작성.

**★ 공고도 DB에 기록**하되 상태를 `자동제외`로 둔다. 이유: (1) 중복 체크를 노션 하나로 끝낼 수 있고 (2) 잘못 걸러진 걸 나중에 확인 가능. 팀 기본 보기는 `상태 ≠ 자동제외`, 적합도·마감일 정렬로 만든다. prefilter에서 떨어진 공고는 기록하지 않는다.

### 6.6 중복·동시 실행

- 처리 기록의 유일한 출처는 노션 DB의 `공고번호`. 로컬 상태 파일 없음 → 누가 돌려도 같은 기준.
- 실행 시작 시 최근 `lookback_days + 여유` 기간 공고번호를 조회해 캐시, 업로드 직전에 한 번 더 확인.
- 두 사람이 정확히 동시에 돌리는 경우의 드문 중복은 허용(v1). 정기 담당자 1명 운영이 기본.
- 정정공고(차수 변경)는 새 행으로 올리고 요약에 "정정공고"를 표시.

### 6.8 prefilter 규칙과 처리량 상한 *(설계자 판단)*

**prefilter (순수 스크립트):**
- 매칭 대상: 공고명 + API가 주는 분류·업무구분 필드. (RFP 본문은 이 단계에서 아직 없음)
- 포함 키워드 하나 이상 매칭 필수.
- 제외 키워드 매칭 시: 포함 키워드도 함께 매칭되면 **통과**(예: "AI 플랫폼 구축 및 유지보수" → Claude가 판단), 포함 키워드 없이 제외 키워드만 있으면 탈락.
- 업무구분은 용역만. 예산 범위 밖 탈락(예산 미기재는 통과).
- 마감: 본공고는 `min_days_to_deadline` 미만 탈락, 사전규격은 의견 마감 경과분만 탈락. 사전규격의 "마감일" 칸에는 의견 마감일을 넣는다.

**처리량 상한:**
- 후보가 `max_per_run`(기본 15)을 넘으면 우선순위(포함 키워드 매칭 수 → 마감 임박 순)로 정렬해 상한까지만 분석.
- 남은 후보는 노션에 없으므로 다음 실행에서 자동으로 다시 후보가 된다. lookback 밖으로 밀려 유실되는 걸 막기 위해 실행 결과 요약에 "미처리 n건"을 표시하고, n>0이면 lookback을 늘리거나 바로 재실행하라고 안내.
- 공고 1건 단위로 분석→업로드를 완료하므로 사용량 한도로 중간에 끊겨도 완료분은 보존된다.
- 서브에이전트 병렬 분석은 v1에서 하지 않는다(사용량 소모가 커짐).

### 6.7 정기 실행

- 기본: 담당자 PC의 Windows 작업 스케줄러로 평일 아침 1회 `claude -p "/g2b-rfp-scout"` 실행 (필요 도구 권한을 미리 허용해 무인 실행 가능하게).
- 실행 로그는 `%USERPROFILE%\.g2b-rfp-scout\logs\`.
- 클라우드 예약 실행(Claude Code routines) 가능 여부는 구현 중 확인, 가능하면 대안으로 문서화.
