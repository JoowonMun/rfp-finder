# 공고 분석 지침

목표: 팀이 **제안서를 써볼 만한가**를 판단하고, 노션 페이지 하나만 읽고 "들어갈지 말지"를 정할 수 있게 정리한다.
판단 기준은 언제나 `config.yaml`의 `team.capabilities`(+ `past_projects`)다. 키워드가 겹치는지가 아니라 **과업의 실체가 팀이 하는 일과 맞는지**를 본다.

## 출력 JSON (이 형식 그대로)

```json
{
  "bid_no": "R26BK00012345",
  "fit": 1,
  "fit_reason": "**생성형 AI 도입 ISP**로 우선순위 낮은 전략 컨설팅, **참가 자격 제한 없음**, 기간·예산 적정 (과업 1 + 자격 1 + 조건 1)",
  "summary": "○○시 생성형 AI 행정혁신 ISP 수립",
  "type": "ISP",
  "detail": {
    "overview": {
      "client": "○○시청 정보화담당관",
      "content": "시 행정 전 분야에 생성형 AI를 도입하기 위한 중장기 전략과 이행계획 수립",
      "period": "계약일부터 6개월",
      "budget": "4억 2,000만 원, 부가세 포함",
      "contract": "제한경쟁입찰, 협상에 의한 계약"
    },
    "requirements": [
      {"title": "행정업무 AI 적용 현황 진단", "details": ["실·국 30개 부서 업무 프로세스 조사 및 AI 적용 가능 업무 발굴", "타 지자체·해외 생성형 AI 도입 사례 벤치마킹"]},
      {"title": "생성형 AI 도입 로드맵 수립", "details": ["3개년 단계별 추진 과제와 우선순위, 소요 예산 산정"]},
      {"title": "AI 거버넌스·보안 가이드", "details": ["개인정보·보안 기준을 반영한 내부 활용 지침 마련"]}
    ],
    "why_fit": ["현황 진단, 목표모델, 이행계획으로 이어지는 **전형적인 AI 도입 ISP 구조**라 팀 방법론을 그대로 적용 가능", "**개인정보 탐지, 외부 API 비용 관리, AI 생성물 표시** 같은 운영 요건이 구체적이어서 **LLMOps 경험**이 있는 팀이 유리"],
    "gaps": ["**데이터 플랫폼 아키텍처 설계**가 일부 포함돼 인프라 설계 인력은 협력사로 보완 필요"],
    "eligibility_risks": ["소프트웨어사업자 신고 필요", "최근 3년 유사 실적 1건 이상 요구 — 실적 확인 필요"],
    "eligibility_checklist": [
      {"item": "소프트웨어사업자 신고", "ok": false},
      {"item": "최근 3년 유사 실적 1건 이상", "ok": false},
      {"item": "공동수급 허용", "ok": true}
    ],
    "duration": "2027년 7월까지",
    "evaluation": "기술 90 : 가격 10",
    "rfp_read": true
  }
}
```

- `fit`: 0~3 정수(0=제외, 아래 기준). `summary`: 한 줄(40자 안팎), 무엇을 하는 사업인지. 실행 결과 보고에만 쓰고 노션에는 올리지 않는다.
- `type`: 노션 **사업유형** 태그. 아래 값 중 **핵심 과업에 가장 가까운 하나**만 고른다. 목록에 없는 값은 쓰지 않는다.
  - `AI 구축`: AI 시스템·서비스·모델·플랫폼을 직접 개발·구축
  - `AI 개발 컨설팅`: 구축 설계, 요구사항 정의 등 AI 개발을 전제로 한 컨설팅
  - `ISP`, `ISMP`: 정보화전략계획, 정보시스템 마스터플랜
  - `전략·마스터플랜`: AI 전환 전략, 비전, 로드맵, 마스터플랜(ISP·ISMP가 아닌 것)
  - `PMO`: 사업관리·PMO
  - `연구용역`: 정책연구, 기획연구, 실태조사
- 목록 필드(`requirements`, `why_fit`, `gaps`, `eligibility_risks`)는 항목이 없으면 빈 목록 `[]`.
- 모르는 값은 지어내지 말고 "제안요청서에 명시 없음"이라고 쓴다.
- **문체(읽기 쉽게):** 괄호와 마침표 약어를 줄인다. 날짜는 "2026년 12월 31일", 기간은 "계약일부터 2026년 12월 31일까지", 금액은 "5,500만 원"·"4억 2,000만 원"처럼 풀어 쓴다. "2026.12.31.", "~", "(부가세 포함)"처럼 기호를 겹쳐 쓰지 않는다. 한 문장에 정보를 몰아넣지 말고 항목을 나눈다.
- **분량:** 노션 페이지가 곧 상세 분석이다. 위 예시 정도로 구체적으로 쓴다.
  - `overview`: 객체로 쓴다. `client`(발주기관, 재원이 있으면 "· 재원: ○○"), `content`(무엇을 하는 사업인지 한두 줄), `period`, `budget`, `contract`. 모르는 항목은 뺀다.
  - `requirements`: 제안요청서의 주요 과업 3~7개. 각 항목은 `{"title": 과업명, "details": [세부 내용 1~2줄]}` — 제안요청서에 적힌 범위·규모·산출물을 구체적으로(숫자가 있으면 숫자로).
  - `why_fit`, `gaps`: 불릿으로 나오니 `requirements` 세부 내용처럼 **명사형 개조식**으로 1~2줄. "~한다.", "~함." 같은 문장 종결과 마침표를 쓰지 않고 "~라 유리", "~ 보완 필요", "~ 적용 가능"처럼 끝낸다. 근거(제안요청서 내용과 팀 역량의 연결)가 드러나게.
- **핵심 키워드 굵게:** `fit_reason`, `why_fit`, `gaps`에서 판단을 가르는 핵심어를 `**키워드**`로 감싼다(노션에서 굵게 표시됨). 과업명·기술·자격 조건·리스크 요인처럼 눈에 먼저 들어와야 할 말만, 항목당 1~3개. 문장 전체나 흔한 말("AI", "사업")은 굵게 하지 않는다. `summary`, `overview`, `duration`에는 쓰지 않는다.
- `fit_reason`: 페이지 맨 위 한줄평이다. "~하다. ~하다."로 이어 쓰지 말고 쉼표로 이은 **한두 구절**로 짧게, 핵심어는 굵게.
  - `evaluation`: 카드에 들어가니 "기술 90 : 가격 10"처럼 짧게.
- `duration`: 노션 **사업기간** 열. 항상 **"2027년 7월까지"처럼 끝나는 연·월**로 쓴다.
  - 제안요청서에 종료일이 있으면 그 연·월("계약일부터 2026년 12월 31일까지" → "2026년 12월까지").
  - "계약일부터 7개월", "150일"처럼 기간만 있으면, 입찰 마감일 다음 달을 계약 시점으로 보고 계산해 앞에 "약"을 붙인다(마감 2026년 12월, 7개월 → "약 2027년 7월까지").
  - 장기계속·다년도 사업은 최종 종료 연·월. 모르면 생략.
- `eligibility_checklist`: 참가 자격 요건마다 `ok` = **누구나/우리 팀이 문제없이 충족하는 조건이면 true**(예: 공동수급 허용, 제한 없음), 팀이 확인해야 하거나 막힐 수 있으면 false. 요건이 없으면 `[]`.

## 적합도 기준

`fit`은 0~3이다. **0은 "맞지 않음"으로 노션 표에 올리지 않고**, 1~3은 표에 올라가는 별 개수다.
후보는 이미 키워드로 걸러진 공고라, 1~3은 "올릴 만한 공고들 사이의 우선순위"를 가르는 용도다.

### 0 (제외): 먼저 이것부터 판단

아래에 해당하면 점수를 매기지 않고 `fit: 0`.
- **AI를 만들거나 AI 도입을 계획하는 과업이 없다**: AI 모델·서비스 개발 요구도, AI 구축·전환 계획 수립도 없으면 제목에 '데이터·빅데이터·지능형'이 있어도 0 (예: 통계·공간 분석 모델, BI·대시보드, 데이터 개방 체계)
- AI가 사업의 핵심이 아니다: 일반 정보화 ISP/ISMP, 일반 시스템 개발·고도화, 인프라(데이터센터·클라우드·네트워크·GPU 서버) 구축 계획
- 본질이 장비·물품 납품, 교육·행사 운영, 운영·유지보수, 감리, 영향평가, 순수 학술연구·정책연구
- `team.capabilities`에 "주력 아님"으로 적힌 분야가 대상이다
- 참가 자격상 **확실히** 참여할 수 없다(예: 특정 지역 본사 필수인데 팀이 해당 없음이 명확함)

**형식보다 대상이 먼저다.** "ISP·마스터플랜·전략" 같은 형식이 팀과 같아도 그 계획의 대상이 AI가 아니면 0. 사업명에 "AX·AI"가 붙어도 실제 산출물을 제안요청서에서 확인한다.

### 1~3: 세 가지를 점수로 매겨 합산

과업 일치는 `team.capabilities`에 적힌 **우선순위 단계**를 그대로 따른다.

| 항목 | 3점 | 2점 | 1점 | 0점 |
|---|---|---|---|---|
| **과업 일치** | `최우선 주력`을 **직접 구축·개발**하는 것이 핵심 과업 | `그다음`에 적힌 일(다른 AI 개발, 개발 컨설팅 등)이 핵심 | `우선순위 낮음`에 적힌 일(ISP·ISMP·전략·비전·마스터플랜 등)이 핵심 | AI 과업이 일부만 있고 나머지가 비주력 (AI 과업이 아예 없으면 0점이 아니라 **제외**) |
| **참가 자격** | — | — | 막히는 요건이 없다(팀 보유 자격으로 모두 충족) | 확인이 필요하거나 걸리는 요건이 있다(미보유 업종 등록, 지역제한, 실적 요건 등) |
| **수행 조건** | — | — | 기간·예산이 과업량에 맞고, 비주력 과업 비중이 작고, 단독 수행 부담이 크지 않다 | 기간이 매우 짧거나 예산이 과업 대비 작음, 비주력 과업 비중이 큼, 공동수급·하도급 불가로 부담이 큼 중 하나 이상 |

**합계 5점 → 3 (★★★ 바로 검토), 4점 → 2 (★★ 검토 권장), 0~3점 → 1 (★ 참고).**

- 최우선 주력 사업은 자격·조건 중 하나가 걸려도 ★★, 우선순위 낮은 컨설팅은 조건이 다 좋아도 ★에 머문다. 의도된 설계다.
- "컨설팅"이라도 구축 설계·요구사항 정의·개발 PMO처럼 **개발을 전제로 한 컨설팅**은 `그다음`(2점), 비전·전략 수립 중심은 `우선순위 낮음`(1점)으로 본다.
- 제안요청서를 못 읽었으면(`rfp_read: false`) **최대 2**.
- `team.past_projects`와 직접 겹치는 수행 실적이 있으면 근거로 `why_fit`에 쓰되, 점수는 위 표대로 매긴다.
- `fit_reason` 끝에 점수 내역을 붙인다(예: "… (과업 3 + 자격 1 + 조건 0)").

**자격 체크리스트:** `team.capabilities`에 적힌 보유 자격(예: 소프트웨어사업자, 중소기업 확인서, 직접생산확인증명서)으로 충족되는 요건은 `ok: true`.

경계 예시 (최우선 주력 = 생성형 AI·RAG·AI Agent 구축, 그다음 = 기타 AI 개발·개발 컨설팅, 우선순위 낮음 = AI ISP·전략인 팀):
- "생성형 AI 민원 챗봇(RAG) 구축", 자격 문제 없음, 6개월·4억 → 3+1+1 = 5 → **3**
- "AI 학습튜터(RAG) 구축", 자격 문제 없음, 기간 1개월·예산 5,500만 원 → 3+1+0 = 4 → **2**
- "AI 영상분석 모델 개발", 자격·조건 문제 없음 → 2+1+1 = 4 → **2**
- "AI 구축사업 PMO", 자격 문제 없음, 기간 적정 → 2+1+1 = 4 → **2**
- "생성형 AI 도입 ISP", 자격·조건 문제 없음 → 1+1+1 = 3 → **1**
- "AI 이상탐지 + 일반 MES 개발 + GPU 서버 구매", 공동수급 불가 → 0+1+0 → **1**
- "데이터 플랫폼·데이터 파이프라인·데이터 품질관리 시스템 구축" → 팀이 "주력 아님"으로 적었으면 **0**
- "빅데이터 분석모델 개발", "AI·빅데이터 기반 통계 분석", "데이터 허브 구축" → 제목에 AI가 있어도 실제 과업이 **데이터 분석·데이터 엔지니어링**이면, 팀이 주력 아님으로 적었을 때 **0**. AI 모델·서비스를 만드는 과업이 핵심인지 제안요청서로 확인한다.
- "AI 적용 차세대 ○○시스템 ISP" → 시스템 고도화가 중심이면 **0**
- "AI 데이터센터 구축 ISMP", "재해복구시스템 마스터플랜", "AI 기반 CCTV 장비 구매", "AI 교육과정 운영" → **0**

## 반드시 확인할 것 (eligibility_risks)

- 참가 자격: 업종 등록(소프트웨어사업자, 엔지니어링 등), 중소기업 제한, 지역 제한
- 실적 요건: 유사 사업 수행 실적 건수·금액
- 공동수급(컨소시엄) 허용 여부, 하도급 제한
- 일정: 제안서 제출 마감까지 남은 기간, 사전규격이면 의견 마감일
- 평가 방식: 기술:가격 비율, 협상에 의한 계약인지

## 제안요청서를 못 읽은 경우

`rfp_read: false`. 공고명·기관·예산·마감만으로 판단하고, `fit_reason` 앞에 "(제안요청서 미확인)"을 붙인다. 요구사항·평가 방식은 "제안요청서 미확인"으로 둔다. **절대 내용을 추측해서 채우지 않는다.**
