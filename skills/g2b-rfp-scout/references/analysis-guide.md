# 공고 분석 지침

목표: 팀이 **제안서를 써볼 만한가**를 판단하고, 노션 페이지 하나만 읽고 "들어갈지 말지"를 정할 수 있게 정리한다.
판단 기준은 언제나 `config.yaml`의 `team.capabilities`(+ `past_projects`)다. 키워드가 겹치는지가 아니라 **과업의 실체가 팀이 하는 일과 맞는지**를 본다.

## 출력 JSON (이 형식 그대로)

```json
{
  "bid_no": "R26BK00012345",
  "fit": 3,
  "fit_reason": "핵심 과업이 생성형 AI 도입 ISP로 팀의 AX 전략 컨설팅과 직접 일치하고 참가 자격 제한이 없음",
  "summary": "○○시 생성형 AI 행정혁신 ISP 수립 (6개월, 4.2억)",
  "detail": {
    "overview": "○○시청 정보화담당관 발주. 시 행정 전 분야에 생성형 AI를 도입하기 위한 중장기 전략과 이행계획을 수립하는 사업으로, 계약 후 6개월, 4.2억(부가세 포함), 협상에 의한 계약.",
    "requirements": [
      {"title": "행정업무 AI 적용 현황 진단", "details": ["실·국 30개 부서 업무 프로세스 조사 및 AI 적용 가능 업무 발굴", "타 지자체·해외 생성형 AI 도입 사례 벤치마킹"]},
      {"title": "생성형 AI 도입 로드맵 수립", "details": ["3개년 단계별 추진 과제와 우선순위, 소요 예산 산정"]},
      {"title": "AI 거버넌스·보안 가이드", "details": ["개인정보·보안 기준을 반영한 내부 활용 지침 마련"]}
    ],
    "why_fit": ["과업이 현황 진단 → 목표모델 → 이행계획으로 이어지는 전형적인 AI 도입 ISP 구조라 팀의 기존 방법론을 그대로 적용할 수 있음", "PoC 기획이 포함돼 있어 팀의 생성형 AI 실증 기획 경험이 차별점이 됨"],
    "gaps": ["데이터 플랫폼 아키텍처 설계가 일부 포함돼 있어 인프라 설계 인력은 협력사로 보완해야 할 수 있음"],
    "eligibility_risks": ["소프트웨어사업자 신고 필요", "최근 3년 유사 실적 1건 이상 요구 — 실적 확인 필요"],
    "eligibility_checklist": [
      {"item": "소프트웨어사업자 신고", "ok": false},
      {"item": "최근 3년 유사 실적 1건 이상", "ok": false},
      {"item": "공동수급 허용", "ok": true}
    ],
    "duration": "6개월",
    "evaluation": "기술 90 : 가격 10",
    "rfp_read": true
  }
}
```

- `fit`: 1~3 정수. `summary`: 한 줄(40자 안팎), 무엇을 하는 사업인지가 바로 보이게.
- 목록 필드(`requirements`, `why_fit`, `gaps`, `eligibility_risks`)는 항목이 없으면 빈 목록 `[]`.
- 모르는 값은 지어내지 말고 "제안요청서에 명시 없음"이라고 쓴다.
- **분량:** 노션 페이지가 곧 상세 분석이다. 위 예시 정도로 구체적으로 쓴다.
  - `overview`: 발주기관·사업 목적·기간·예산·계약방식을 2~3문장으로.
  - `requirements`: 제안요청서의 주요 과업 3~7개. 각 항목은 `{"title": 과업명, "details": [세부 내용 1~2줄]}` — 제안요청서에 적힌 범위·규모·산출물을 구체적으로(숫자가 있으면 숫자로).
  - `why_fit`, `gaps`: 항목마다 1~2문장, **근거(제안요청서 내용 ↔ 팀 역량)**가 드러나게.
  - `evaluation`: 카드에 들어가니 "기술 90 : 가격 10"처럼 짧게.
- `duration`: 사업 기간 한 마디("6개월", "계약일~2027.12."). 모르면 생략.
- `eligibility_checklist`: 참가 자격 요건마다 `ok` = **누구나/우리 팀이 문제없이 충족하는 조건이면 true**(예: 공동수급 허용, 제한 없음), 팀이 확인해야 하거나 막힐 수 있으면 false. 요건이 없으면 `[]`.

## 적합도 기준

| 적합도 | 기준 |
|---|---|
| **3 (★★★)** | 사업의 **대상(무엇을 계획·수행하는지)**과 **형식(어떻게: 컨설팅·ISP·구축 등)**이 둘 다 팀 역량과 직접 일치하고, 참가 자격에서 막히는 부분이 없다. |
| **2 (★★)** | 일부만 일치한다(예: 구축 비중이 크지만 컨설팅·기획 파트가 있음). 또는 과업은 맞는데 자격·실적 리스크가 있다. |
| **1 (★)** | 키워드만 겹치고 실질적으로는 맞지 않는다. 노션 표에는 올리지 않고 로컬 제외 기록에만 남는다. |

**형식보다 대상이 먼저다.** "ISP·ISMP·마스터플랜·전략" 같은 컨설팅 형식이 팀과 같아도, 그 계획의 대상이 팀의 주력 분야가 아니면 ★★★를 주지 않는다. 사업명에 "AX·AI"가 붙어 있어도 실제 산출물이 무엇인지(인프라 구축 계획인지, AI 전환·활용 전략인지)를 제안요청서에서 확인한다. `team.capabilities`에 "주력 아님"으로 적힌 분야가 대상이면 **1**.

경계 예시 (팀 = AX 컨설팅일 때):
- "AI 데이터센터 구축 ISMP", "클라우드 인프라 전환 ISP", "재해복구시스템 마스터플랜" → **1**. 형식은 컨설팅이지만 대상이 인프라(센터·서버·네트워크) 구축 계획이다.
- "AI 적용 차세대 ○○시스템 ISP" → **2~3**. 시스템 고도화가 중심이면 2, AI 적용 방안 수립이 핵심 산출물이면 3.
- "차세대 ○○시스템 ISMP", "○○정보시스템 ISP"처럼 AI가 핵심이 아닌 **일반 정보화** 컨설팅 → 팀 설정이 일반 정보화를 주력으로 적지 않았다면 **1**.
- "AI 기반 CCTV 장비 구매" → **1**. 물품·장비 납품이 본질이다.
- "AI 교육과정 운영 용역" → **1~2**. 교육 운영이 본질이면 1, AI 도입 교육 설계·컨설팅 성격이면 2.
- "공공데이터 AI 플랫폼 구축(컨설팅 일부 포함)" → **2**. 구축 주도 사업이라 단독 수주는 어렵지만 컨소시엄 컨설팅 파트가 가능하다.
- "AI 플랫폼 구축 및 유지보수" → 유지보수 비중을 본다. 대부분 운영·유지보수면 **1**.
- "생성형 AI 도입 ISP/ISMP", "AI 전환 전략 수립" → 자격 문제가 없으면 **3**.

## 반드시 확인할 것 (eligibility_risks)

- 참가 자격: 업종 등록(소프트웨어사업자, 엔지니어링 등), 중소기업 제한, 지역 제한
- 실적 요건: 유사 사업 수행 실적 건수·금액
- 공동수급(컨소시엄) 허용 여부, 하도급 제한
- 일정: 제안서 제출 마감까지 남은 기간, 사전규격이면 의견 마감일
- 평가 방식: 기술:가격 비율, 협상에 의한 계약인지

## 제안요청서를 못 읽은 경우

`rfp_read: false`. 공고명·기관·예산·마감만으로 판단하고, `fit_reason` 앞에 "(제안요청서 미확인)"을 붙인다. 요구사항·평가 방식은 "제안요청서 미확인"으로 둔다. **절대 내용을 추측해서 채우지 않는다.**
